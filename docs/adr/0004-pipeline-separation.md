# 0004. 수집 파이프라인과 전달 파이프라인 분리 원칙

- **날짜**: 2026-04-20
- **상태**: Accepted

## 배경

AXIS의 AI 처리 흐름을 처음 설계할 때 단일 LangGraph 그래프로 크롤링부터 Slack 발송까지 전체를 처리하는 방안을 검토했다.

그러나 두 흐름의 실행 주기와 입력/출력이 근본적으로 다르다.

| 구분 | 수집 파이프라인 | 전달 파이프라인 |
|---|---|---|
| 실행 주기 | 1시간마다 | 매일 오전 8:30 |
| 입력 | 외부 뉴스·공시·채용공고 | PostgreSQL 이슈 카드 |
| 출력 | PostgreSQL + Qdrant 저장 | Slack 브리핑 |
| 실패 허용 | 일부 실패 허용 (재시도) | 전체 성공 필요 |

## 결정

수집 파이프라인과 전달 파이프라인을 **별도 LangGraph 그래프**로 분리한다. 두 파이프라인은 **PostgreSQL을 통해서만** 데이터를 교환한다 (직접 호출 금지).

```
수집 파이프라인 (매시간)
  크롤링 → 전처리 → 품질Gate → 신뢰도Gate → 중복Gate → 임베딩 → [PostgreSQL + Qdrant 저장]

전달 파이프라인 (매일 08:30)
  [PostgreSQL 이슈 카드 조회] → 시사점 생성 → SC 검증 → Slack 발송
```

## 대안

| 대안 | 기각 이유 |
|---|---|
| 단일 LangGraph 그래프 | 수집 지연이 브리핑 지연으로 전파. 디버깅 복잡. 부분 재실행 불가 |
| 수집 완료 시 전달 트리거 | 수집이 여러 번 실행될 때마다 전달 파이프라인이 중복 실행될 위험 |

## 근거

- **독립 스케줄링**: 수집 실패가 브리핑 지연으로 전파되지 않음
- **재실행 가능성**: 수집 데이터는 PostgreSQL에 누적되어 있으므로, 전달 파이프라인만 단독 재실행 가능
- **디버깅 용이성**: 각 파이프라인의 입력/출력이 명확히 분리됨
- **LLM 비용 격리**: 전달 파이프라인(GPT-4o 시사점 생성)의 비용을 별도 추적 가능

## 영향

- `axis-ai/src/pipeline/ingestion_graph.py`와 `delivery_graph.py`를 별도 파일로 관리
- SpringBoot Scheduler가 각각 `/pipeline/run`과 `/pipeline/delivery`를 독립 호출
- 두 파이프라인 간 직접 함수 호출 금지 — 항상 PostgreSQL 경유
- `pipeline_logs` 테이블에 `pipeline_step`으로 각 단계별 실행 이력 추적
